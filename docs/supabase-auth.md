Hosted workspace is now Supabase Auth with SSR cookies. Existing workspace row and its reports remain unchanged until owner linking. Initial setup: create a confirmed email/password user in Supabase Dashboard > Authentication > Users, open /auth/setup with existing Basic credentials, enter the new user's credentials. Atomic binding updates only the existing workspace's auth_user_id and email, preserving its UUID and all reports. After binding, Basic credentials no longer work and setup is closed. No public signup or automatic account creation. Only confirmed nonanonymous owner UUID accepted. RLS existing server-only DB token stays unchanged; no secret key is sent to browser. Private share routes and paid-provider endpoints require auth. Local SQLite mode remains unchanged. Remove APP_ACCESS_USERNAME and APP_ACCESS_PASSWORD after successful setup and redeploy; not needed for Supabase mode once bound. If a user needs account recovery, use Supabase Dashboard; password reset/self-service not implemented. Tests use mock Auth responses, not live login. Do not put real passwords in logs or env. For full recovery, an authorized project administrator can create a new verified user and manually reassign the existing workspace auth_user_id after verifying identity.
